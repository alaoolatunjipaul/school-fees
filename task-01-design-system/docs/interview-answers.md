# Interview answers

## Q10: Why is your display large line height that number and not one step either side?

I used 1.4 for display large because large text needs proportionally less line spacing than body text. A heading is a few words over two or three lines, so the eye does not have to travel back from the end of a long line, which is what extra spacing helps with. 1.4 is also the tightest value my brief allows, so it keeps the heading compact. At 57px that gives 79.8px. One step up, 1.5, would be 85.5px, and 1.6 would be 91.2px. On a small phone a display heading wraps onto several lines, so every extra pixel of line height pushes the amount owed further down the screen, and the amount is what the parent came for. A looser value would also make the lines of a big heading look like separate pieces. One honest note: the token export rounded 79.8 to 80, so my CSS holds 1.40351 and not exactly 1.4. I have not tested these values on a real phone.

## Q11: One place in your token structure you would build differently

If I started again I would build the palette layer first. My Figma file has 62 colour variables, and only two of them, Primary and Surface Tint, point at the palette (tokens.css lines 9 and 10). The other 60 hold a typed hex. I found this on a branch, when I changed the source colour: the button followed it and the header did not, and nothing warned me. What I would do instead is put the full tonal palette in the ref collection, from tone 0 to tone 100, and make every role an alias of one tone, so a rebrand is a single edit at the source. The cost is real. It is many more variables to build, and the plugin wrote its own typed copy of my colour into each role, so I would have to keep checking that nothing drifted back. It would also have delayed my first working screen. I would still do it, and I would check the exported JSON for aliases before building anything on it, because my first export had none.

## Q12: Wrong-answer analysis

The candidate has copied values out of Figma and called the result a source of truth. A source of truth needs two things this setup does not have. First, relationships. If every colour role is exported as its own hex, each role holds a private copy, so changing the brand colour means finding and changing every copy. In my own file only two of 62 colour variables pointed at the palette, and when I changed the source on a branch the button followed and the header did not, with no error. Second, enforcement. A CSS file full of hex values does not stop anyone typing a hex into a component. When an agent that had never seen my system built a screen, a search found 34 raw colours and none was my brand colour. In month four a rebrand arrives, someone updates Figma and re-exports, and the product comes out half one colour and half the other, and nobody is told. The fix is roles that reference palette tokens, plus a search for raw colour values across the whole codebase.

## Q9: Why do AI-generated interfaces look generic, and what do you hand an agent to stop it?

With nothing supplied, an agent produces the most likely interface for an unspecified request, and that is not a failure on its part. It is the correct output for "make it look good". When I asked an agent for my fees screen with no system, it invented a palette of ten colours, added gradients, glows, a gold button and a "2nd Term" badge I never asked for, and a search found 34 raw colour values, none of them my brand colour. To stop that, I handed it three things. First, the tokens as a CSS file it could read, with colours as roles and not raw values. Second, rules in the prompt: no raw colours, no primitive colours, no gradients, and text only from the type styles. Third, a way to check it, because I then searched the file and asked which style it used for specific elements, and compared its answers with the code. The search found 0 raw colours. The agent still added a "Parent portal" line, so tokens control style but not content.

## Q1: How would you structure design tokens?

I would structure tokens in layers, where each layer can only point at the one below it. The bottom layer holds raw values, such as palette tones and sizes. The middle layer holds roles named for their job, such as primary or on-surface, and each role is an alias of a palette token and not a copy of its value. If a component layer is needed, it points at a role, for example a button background pointing at primary. Names say what something is for and not what colour it is, so a role keeps its name when the colour changes. The interface may use only roles, never the raw layer, so a change at the bottom reaches everything above it. In my own file this is the ref collection and the material-theme collection, and the export writes the link as {ref.primary.40}. I only finished it for two roles, and the other sixty are typed values, which is the weakness in my structure.

## Q2: When is a token change breaking?

A token change is breaking when something that uses the token stops working or looks wrong without its owner having changed anything. Renaming or removing a token is the clearest case. In CSS a missing custom property does not raise an error, it makes the declaration silently fall back, so the page just looks wrong. Changing a token's unit or type is breaking too: my line heights are unitless ratios and my letter spacing is in em, and turning either into a fixed length would break every consumer that relies on scaling. Changing a value can be breaking if it crosses a limit. My button text on primary measures 7.56:1, so a lighter primary could fail contrast. Repointing an alias at a different token also counts. Adding a new token is not breaking, and neither is adjusting a value in a way that keeps its meaning and still passes the checks. So I would treat renames, removals, unit changes and anything that breaks a recorded contrast pair as breaking, and say so in the version note.

## Q3: How would you support multiple brands and themes?

I would keep brands and themes as two separate things. A theme, such as light and dark, is the same brand with different values for the same roles. In Material, light mode picks darker tones from the palette, for example primary at tone 40, and dark mode picks lighter ones, such as tone 80, so one palette covers both. In Figma that is a second mode on the role collection, and in CSS it would be the same role names redefined under a theme attribute. A brand is different: it replaces the palette at the bottom layer, and because roles point at the palette, the components do not change. My own file only partly supports this. It has a light column and no dark one, because my parents pay in daylight on a phone, and I have not tested dark mode with any of them. A second brand would also be hard today, because only two of my sixty-two colour variables point at the palette, so I would have to edit sixty by hand.

## Q4: Can tokens guarantee accessible contrast?

No, tokens cannot guarantee accessible contrast, because contrast belongs to a pair of colours and a token holds only one. A token has no idea what it will be placed on. My primary-container colour is fine as a fill, but against my page surface it measures 1.23:1, so it cannot mark a boundary on its own. My primary50 is 4.47:1 on white, just under the 4.5:1 text threshold, so it is a valid token that fails as text. Tokens also cannot see opacity overlays, text size or weight, or whether meaning depends on colour alone: my error, warning and success colours all pass contrast yet sit at about 1.0:1 against each other, so they must carry an icon and a word. A tool can also be wrong. Figma kept a description saying AAA fail after I changed the hex to one that passes. What tokens can do is define role pairs, such as on-primary on primary, and let me test every pair I use and record the ratio. I measured mine with WebAIM and kept the results.
